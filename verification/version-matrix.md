# Installer 版本测试矩阵与选择理由

设计日期：2026-09-16。**本文是目标测试方案，尚未接入 CI，不是新一轮验收结果。** 当前 rc.6 实际跑过的真实版本组合仍为 1.0.31→1.0.32，且为未登录冷态；运行中故障由可控原生进程测试覆盖。

## 1. 四个版本变量分别记录

| 名称 | 定义 | 为什么需要 |
| --- | --- | --- |
| I | 本次待测 installer 的提交、版本、每个平台二进制 SHA-256 | Computer 没变，installer 自己也可能引入迁移回归。不能只报告 Computer 的版本对。 |
| L | 固定历史起点：**Computer 1.0.17** | 给旧版兼容留一个永不随 latest 滑动的样本，长距离升级可持续复现。它是历史代表，不宣称是支持下限，也不代表所有更旧版本。 |
| R | 固定参考版：**Computer 1.0.32** | I 改动时，以固定 L→R 区分 installer 回归与新 Computer／渠道变化；也是当前切换独立 installer 前的稳定参考。 |
| M / C | M 是本次开始时解析并冻结的 main；C 是显式指定的待发 Computer 候选 | M 验证当下用户拿到的产品；C 在新产品进入 main 前验证。候选必须有可下载、可校验的原生产物，不能用版本标签伪装其他字节。 |

1.0.17 与 1.0.32 的公开 manifest 均包含五个平台，元数据及哈希快照见 [baselines/published-2026-09-16.json](baselines/published-2026-09-16.json)。这次只核了 manifest，不等于重新执行了这些二进制。

选择 L 的源码依据：[1.0.17 的 CLI](https://github.com/botiverse/slock/blob/computer-v1.0.17/packages/computer/src/cli.ts) 的 `status` 是文本接口，未注册 `--json`；其源码已有 K 适配文件。因此它可以代表较早产品和旧接口，**不能称为“完全没有 K 的版本”**。1.0.32 的 CLI 同样没有这个 JSON 选项；两者的价值不是“一有一无 JSON”，而是固定历史跨度与固定回归对照。完全没有 status、stop 失效等情况继续由有明确行为定义的 fixture 测试，不把合成故障冒充某个真实历史版本。

首次包含新 installer 接入的 Computer 正式发布后，再冻结 **N = 该真实发布版本**，用于长期验证“已接入 installer 的 Computer 自身发起升级”。目前 N 未发布，不猜版本号，不先写通过。它新增的是入口兼容边界，不是为了多一个数字。

## 2. 必测的版本边，不做任意两两组合

每个箭头均是独立、可重建的起始环境。除标注的重复升级外，目标应高于起点。

| ID | 安装／版本路径 | 运行频率 | Rationale |
| --- | --- | --- | --- |
| F | 空目录 → M；有 C 时另跑空目录 → C | installer 发布、Computer 候选发布 | 新装没有旧状态，不能拿升级成功代替新装。 |
| A | L → R | installer 发布；修改版本解析／状态迁移／停止／修复时 | 起点终点都固定，是 installer 回归的稳定对照，不受 latest 移动干扰。 |
| B | L → M | installer 发布、定时集成验证 | 固定老用户跨多个版本直升当前产品，防止只测相邻版本而遗失历史兼容。 |
| C | R → M；有候选时 R → C | installer 发布、Computer 候选发布 | 覆盖较近期安装直升，避免只有很老布局可用、近期布局反而失败。 |
| D | L → C | Computer 候选发布 | 发布前就发现新产品与旧安装不兼容，不能只等 C 变成 main 后再发现。 |
| E | N → M / C（N 发布后启用） | 接入变更、Computer 候选发布 | 真正经过新版 Computer upgrade 接口启动 installer，验证远程回执与完成通知；已登录部分按手工文档执行。 |
| U | T → T，T 为本次 M 或 C | 每个发布目标 | 验证幂等和无需升级，不误停服务、不破坏文件。 |
| G | R → L，先默认拒绝，再显式允许 | installer 发布、降级策略变更 | 单独验证拒绝与明确许可。自动化只覆盖未登录冷态；不保证生产业务数据可逆。 |

- 若 M=R，B 与 A 是同一条产品字节边，只执行一次安装升级并分别记覆盖；C 中 R→M 归 U，不能算升级成功。M=C 时也按不可变产物身份去重。
- **字节边可以去重，解析入口不能省掉。** 固定版本与真实 channel 解析分别做契约检查，至少一个实际 `--channel main` 路径必须证明选中的就是冻结的 M。当前 `real.py` 先解析 latest 再用 `--version`，还不证明 channel 安装入口执行成功。
- 不规定“所有旧版本→所有新版本”。版本数量会无界增长，且很多组合没有新增兼容边界。新增一条长期基线必须说明独特的持久状态或协议变化；事故版本可增为有明确触发条件的回归样本。
- 选择 L 不构成放弃更早版本支持的裁定。新增最老支持版或替换 L 需要明确产品支持范围和覆盖迁移记录，不能悄悄把 L 改成昨天的版本。

## 3. 安装来源与运行状态是独立维度

同一版本不等于同一安装状态。真实产品冷态至少覆盖以下两类：

1. **已有安装接管**：准备该历史版本真实安装留下的目录、sidecar、安装路径与状态快照，记录产生方式。若只是删除新 installer 的 K 状态来模拟旧布局，报告为“重建的接管布局”，不能声称跑过原历史安装器完整迁移。
2. **新 installer 管理的升级**：先用 I 安装 A，再用 I 升级到 T。它验证本工具自己的状态往返，不替代第 1 类。

已有旧 K／服务管理器遗留布局，仅在已获得可重建的真实快照时加入产品用例；否则列 NOT_RUN，合成状态继续放在 fixture 层。不能仅凭版本号推断机器受 launchd、systemd 或某个 K 布局管理。

运行状态分三层报告：

| 层 | 程序及环境 | 能证明什么 |
| --- | --- | --- |
| 自动化原生故障测试 | 可控 Computer-shaped 程序，真实 OS 进程／文件／网络 | 运行、停止、崩溃、回退、强制退出、worker 中断、损坏和恢复策略；不证明真实登录／agent 协议。 |
| 自动化真实产品冷态 | 官方原生 Computer 与 sidecar，隔离目录、未登录、服务停止 | 真实版本与文件／接口兼容，升级后保持停止；不证明登录后的恢复。 |
| 手工真实产品热态 | 测试账号、真实服务及 agent | 进程更替、登录保留、agent 恢复、服务端完成通知；执行 [手工清单](manual-authenticated-upgrade.md)。 |

不把故障注入与全部历史版本做乘积：通用状态机故障在 fixture 层系统覆盖，真实产品用少量有代表性的路径验证集成。真实运行中测试至少在每个支持 OS 上执行接口路径和历史接管路径；架构未跑的仍单独注明。

## 4. CI 成本与发布安排

- **普通提交**：保留五个平台的原生行为／故障测试。涉及核心安装行为的变更，再跑固定 L→R 真实冷态；文档改动不需要额外版本下载。
- **installer 发布候选**：五个平台跑 F/A/B/C/U/G 的适用且去重后的真实冷态路径，此外跑五平台完整 fixture 套件。不得自动把缺失的历史产物换成相邻版本。
- **Computer 候选发布**：以正在发布使用的 installer 版本为 I，五平台跑 F/C/D/U；N 可用后增加 E 的冷态部分，热态按手工记录。C 可以是 prerelease，解析器必须支持真实候选版本，当前只接受三段数字的限制需要修改。
- **定时集成**：每天解析一次 M，跑 L→M 及 channel 解析／下载身份检查。发现回归归因于具体 I、M 和元数据变化，不覆盖固定 L→R 的历史记录。
- **公开发布后**：读取五个平台的不可变下载、校验文件并与 CI 哈希比对；选代表机器跑公开 bootstrap。公开文件可取不等于产品已经升级成功。

这些是本方案建议的验收安排，不追溯宣称 rc.6 已跑新矩阵，也不擅自新增现有 PR 的合并闸门。真实登录场景已约定之后手工执行，留明 NOT_RUN。

## 5. 冻结输入和结果合同

一次调度先生成不可变 execution plan，所有平台使用同一份，不各自解析 latest：

```text
plan_id / matrix_revision / installer commit + version + per-target SHA-256
baseline id + exact Computer version + source tag
manifest URL + original manifest SHA-256 + binary/sidecar SHA-256 + size
main resolved version/release identity + resolved UTC time
candidate identity (optional), selected cases, OS/architecture, initial layout/state
```

保存固定基线的 manifest 和产物身份；每次下载验证它们。字节改变、404、缺少平台或渠道解析失败均显式失败／阻塞该项，不跳绿、不静默回退 fixture。日常网络故障允许有上限的重试，但不修改被冻结的输入。

每条边记录 PASS / FAIL / NOT_RUN / NOT_APPLICABLE，以及理由、实际版本、退出码、receipt、冷／热状态、清理结果。平台上从未存在的产物只能有带证据的 NOT_APPLICABLE，不能冒充五平台通过；本次 L/R 的 manifest 五个平台均有条目。

## 6. 与当前实现的差距

已具备：五平台 fixture、真实冷态 harness、`--older` / `--current` 指定版本、manifest 校验、发布后字节读回、手工热态清单。

尚需实现：固定基线输入驱动、调度前统一冻结执行计划、候选 prerelease 支持、按字节去重但保留 channel 入口验证、真实历史安装布局快照、分用例结果持久化及上述 CI 触发策略。不能直接把现有七步流程对每个版本对重复运行就称为矩阵完成：它把升级、降级、接管、修复串在同一个目录，独立用例应从明确的初始状态开始。
