# 已登录、真实 agent 的手工升级验收

状态：**待执行，本文不是通过记录**。用于补充自动化的未登录冷安装和可控进程故障测试。

目标：用户从 Computer 升级入口发起请求后，旧进程实际退出，新服务加载指定版本，真实 agent 能继续工作，服务端正确显示升级结果。单看下载成功、installer 返回 0 或 Computer 在线均不算通过。

## 本轮具体版本选择

完整理由见 [版本矩阵](version-matrix.md)。本清单按以下明确组合填写，不能自行取相邻最新版：

- 历史版本接管：固定 **1.0.17 → 1.0.32** 为回归对照；另测 **1.0.17 → 本轮明确候选 C／开始时冻结的 main M**，相同产物不重复跑。
- 较近期安装：固定 **1.0.32 → C／M**。若终点仍为 1.0.32，只算幂等，不算升级。
- Computer upgrade 新接口主用例：起点必须是**首个实际包含新 installer 接入的发布版 N**，终点为更高的 C／M。N 尚未发布，当前这一格标 NOT_RUN；不能用 1.0.17 或 1.0.32 的旧升级路径充数。发布后把真实版本号填入记录并固定。
- 尚无更高目标时，不虚构版本、不重标已有二进制。旧版通过公开脚本／Electron 备用入口的验证可以先做，但与新接口分开记。

## 准备

- 使用可重建的专用测试机和测试账号／服务器，不使用承载日常工作或当前验收操作员的机器。操作员从另一台机器观察。
- 分别记录 Windows x64、macOS、Linux 的结果；一个平台的通过不能代替另一个。平台架构也要记录。
- 安装已知起点版本 A；准备明确的目标 B。A 必须实际支持将要测试的入口。测试新 installer 接入时，确认发起升级的 Computer 已包含该接入，不能拿仍走旧升级器的请求充数。
- 旧版不支持升级接口的场景单列为“公开脚本／Electron 备用入口接管”，不能算成 Computer upgrade 接口通过。
- 使用固定起点，不自动挑“最新版本的上一版”。每次填写选择 A 的理由（例如旧安装布局、缺少新 status 接口、已接入 installer 的版本）。
- 分别安排 A→指定候选 B、A→main 最新版。后一项在开始时记录 main 解析到的版本、不可变发布地址、SHA-256；运行中不要改渠道指向。若 A=B，记录为重复升级，不能替代版本变更用例。
- 通过该版本公开的 login/setup/attach 流程登录测试服务器。不要拷贝生产凭据或只改环境变量切换现有连接。
- 记录 installer、Computer、server、Electron（如适用）的版本／提交和 artifact SHA-256，测试开始时间、安装目录、数据目录、所用入口。尚未发布的接入不能记成“发布版本已验收”。
- 在同一测试 Computer 上建立真实 agent，确认它能响应消息并执行一次无害命令。选一个测试目录文件写入随机标记，记下哈希，后续验证保留。
- 记录旧 service、runner、agent/runtime 子进程的 PID、创建时间和可执行路径。Windows 可用 `Get-CimInstance Win32_Process`；Unix 可用 `ps` 和平台进程工具。PID 单独不构成身份；不要收集含 token 的命令行或环境变量。

## 主用例：Computer upgrade 接口

1. 在测试服务器 UI 的 Computer 页面选择目标 B，使用产品提供的升级动作。若该界面不能指定版本，使用已有公开升级客户端；记录实际请求的目标或渠道。不要改用直接执行 installer 来替代这一用例，也不要编造内部 HTTP 请求。
2. 记录请求 ID、操作开始时间和界面返回值。`started`／`accepted` 只表示开始，不表示完成。
3. 从另一台机器观察断连和恢复；保存状态变化时间。默认观察上限 5 分钟，若测试前已规定其他时限则事先记录。超时记失败／待调查，不以不断延长时间判通过。
4. 核对旧 service、runner 以及被替换的 runtime 进程身份已经退出；即使 PID 被复用也能区分。核对新服务、runner 路径／版本，没有重复常驻 owner。保留下来的非替换进程需说明设计原因。
5. 分别读取磁盘 CLI 版本与运行中服务上报的加载版本，均应为 B；不能仅用 `--version` 推断服务已经切换。
6. 给原 agent 发送新的随机标记，要求读取先前测试文件并返回标记及文件哈希。确认是在升级后的会话中真实执行，不能把旧回复当恢复。核对 agent 身份、服务器连接、测试文件保持，未要求重新登录。
7. 查看本次 installer receipt 与服务端升级记录：请求 ID、解析后的目标版本、结果一致；旧进程退出证据与实际观察相符；服务端在新服务就绪后收到完成通知，而非只记录“已接受”。缺少任意一侧证据记为未验证。
8. 确认没有升级结束后仍占用旧安装目录的进程；已完成操作的临时下载／过时恢复副本清理，必要状态和小型回执保留。用户数据不删除。

通过标准：以上步骤全部满足。分别记录安装执行、运行恢复、agent 可用、服务端完成通知四项，不能用其中一项代替其他项。

## 独立补充用例

每例从独立快照或重建环境开始，避免前一例污染结论。

| 用例 | 操作 | 通过标准 |
| --- | --- | --- |
| 运行中 agent | 让 agent 执行一个可中断、无外部副作用的测试任务，过程中升级 | 恢复后可响应新消息；原任务的中断／续接状态符合产品约定，没有重复执行有副作用操作。事先记录是否承诺续接，不自行假定无缝续跑。 |
| 已停止状态 | 保持登录信息，停止 Computer，使用公开脚本升级 | 升级后保持停止；手动启动后无需重新登录，原 agent 能工作。这不是远程接口用例。 |
| 重复操作 | 对已到 B 的安装再次请求 B | 不产生多份服务、不破坏数据；产品明确报告无需升级或已有结果。记录是否同一请求 ID。 |
| 旧版接管 | 用固定的旧版安装／数据布局，走公开脚本或 Electron 备用入口到 B | 接管后版本、原登录／附件、agent 可用性和清理均正确；只确认该旧版边界，不外推所有旧版。 |
| Electron 正常入口 | standalone Computer 可远程升级时，在 Electron 点升级 | 实际走 Computer upgrade；满足主用例，应用恢复显示正确版本。 |
| Electron 备用入口 | standalone 旧版无法远程升级、产品提供备用动作时执行 | Unix install.sh／Windows install.ps1 启动新 installer；升级后原连接与 agent 可用，不生成第二个 owner。 |
| Electron 内置 Computer | 使用随应用打包的 Computer | 不调用 standalone installer 替换应用包；通过应用升级后核对内置服务与 agent。应用发布验收另行记录。 |
| 下载失败 | 在专用测试机上令目标下载不可达，然后发起升级 | 不误报完成；现有服务／agent 仍可用，恢复网络后可用新请求成功升级。 |

运行中崩溃、强杀、回退的可控进程测试已有自动化覆盖。若要在真实已登录产品上复测这些破坏性场景，另开测试快照，明确故障注入时机与预期恢复；不要随意杀共享机器上的进程。

## 失败及证据

- 首次失败先记录时间、请求 ID、界面错误、前后进程身份、版本和数据哈希。停止后续用例，不先重装抹掉现场。
- 本地回执位于 `<RAFT_HOME>/computer/installer/receipts/`；按回执内容的请求 ID 对应，不猜文件名。保留相关 installer、service、runner 日志片段及服务端该操作记录。
- 原始日志和回执仅存测试机受控目录。提交报告前脱敏，不上传登录文件、环境变量、令牌、私钥或完整未经检查的日志。
- 修复／回退后另记“恢复结果”，不能把恢复成功改写成原升级通过。未解决状态保留所需恢复文件。
- 测试结束通过产品提供的 detach/logout/stop 流程撤销测试连接，确认测试进程已退出，再清理专用目录；不删共享用户目录。
